# AGENTS.md

このリポジトリで作業する AI エージェント（Claude Code / Cursor / codex / antigravity 等）が従うべきルール。
プロジェクト全体のマネージメント方針（別管理のチーム共有ドキュメント）の抜粋・運用ルール。

---

## 守るべき基本原則

1. **Single Source of Truth**: タスク・進捗・議論は Issue とボードに集約する。口頭合意や会話ログを根拠にしない。
2. **完了条件が明文化されていない作業はしない**: Issue に完了条件が無い場合は、先に完了条件を確認・追記する。
3. **検証できないものは作らない**: 実装したら必ず動作確認手段（テスト・再現手順）を提示する。
4. **1 タスク = 1 セッション**: タスクが変わったら新規セッションで再開する。
5. **不明点は勝手に決めない**: 仕様が曖昧なら実装前に必ず確認する。

---

## コード品質

- **DRY 原則**: 同一ロジックの重複禁止。共通化して 1 箇所にまとめる
- **SOLID 原則**: 単一責任 / 開放閉鎖 / リスコフ置換 / インターフェース分離 / 依存性逆転
- **ファイル分割**: 1 ファイル 1,000 行超は機能別に分割する

※ 言語別の詳細規約（命名・型・class 使用可否 等）は、技術スタック確定後に `src/*/AGENTS.md` として追加する。

## ブランチ・PR 運用

### ブランチ戦略

- `main` / `develop` への直接 push は**禁止**（Ruleset で保護済み）
- 作業は必ずフィーチャーブランチから PR 経由
- ブランチ名: `feat/<issue番号>-<簡潔な説明>`（例: `feat/12-user-login`）
- 種別プレフィックス: `feat/` / `fix/` / `docs/` / `refactor/` / `chore/`

### PR と Issue のリンク

| 状況 | 書き方 |
|---|---|
| 1 PR で完結 | `Closes #xxx` |
| 複数 PR の途中 | `Part of #xxx` |
| 複数 PR の最後 | `Closes #xxx` |

### PR 作成時のチェック

- [ ] Issue の完了条件を満たしている
- [ ] 動作確認の手順を PR 本文に記載
- [ ] `main` への直接マージではなく `develop` 経由

---

## コミット規約

**Conventional Commits** を使用する。

```
<type>: <subject>

[optional body]
```

| type | 用途 |
|---|---|
| feat | 新機能 |
| fix | バグ修正 |
| docs | ドキュメントのみ |
| refactor | 挙動を変えないリファクタ |
| test | テスト追加・修正 |
| chore | ビルド・ツール設定等 |

---

## Issue / タスク運用

- 開発を伴うタスクは **Issue**、それ以外は **Project の Draft Item** で管理
- Issue には必ず以下を記載：

  ```markdown
  ## 概要
  ## 背景
  ## タスク内容
  ## 完了条件
  - [ ] ...
  ```

- ストーリーポイント: フィボナッチ (1/2/3/5/8/13)。**8 以上は分割を検討**。
- ステータス: `Todo` / `In Progress` / `Pending`（外部待ち） / `Frozen`（凍結） / `Done`

---

## ドキュメント運用

- 運用手順・規約・アーキテクチャは `docs/` 配下に Markdown で管理
- ドキュメント変更も PR レビューを通す
- **「なぜそうしたか」「やってはいけないこと」を書く**。コードを読めばわかる内容は書かない
- この `AGENTS.md` もチーム共有ドキュメントとして扱う（個人設定は `~/.claude/` 等に置く）

---

## AI エージェント利用時の推奨運用

- **Plan Mode を使う**: 大きなタスクはまず計画を立てさせ、確認してから実装を指示する
- **プロンプトに検証基準を含める**: 「〜を実装して」だけで終わらせず、「〜を満たし、〜で動作確認する」まで書く
- **2 回修正してもうまくいかない場合はリセット**: 学びを反映した新プロンプトで再開する方が結果が良い
- **長時間中断する場合は引き継ぎドキュメントを作成**する

---

## レビュー体制

- PR は **3 年生レビュー** → 承認後マージ（Ruleset: 承認 1 名必須）
- マージで Issue 自動クローズ
